SIEM & Detection

Multi-Tenant SIEM False-Positive Tuning & Scoped Exclusions

Systematic approach to auditing noisy recurring alerts in an MSSP queue and proposing scoped exclusions without creating security blind spots.

SIEMMITRE ATT&CKTuningMSSPSigma Rules

Incident Scenario & Environmental Context

Repeated benign vulnerability scanner and backup agent alerts flooded L1 shift queues across three client tenants in an MSSP environment, contributing to alert fatigue and threatening SLA commitments.

Investigation Workflow

1. Audited recurring alerts over a 14-day baseline, grouping by rule ID, affected host, and initiating parent process. 2. Verified authorized maintenance schedules, scanner IP allocations, and backup software service accounts directly with client IT teams. 3. Drafted tightly scoped exclusion criteria restricted to the intersection of signed binary hash, initiating source IP, and specific destination ports. 4. Modeled proposed exclusion logic in Sigma / KQL rules and backtested against 30 days of historical telemetry to ensure no malicious activity was suppressed. 5. Submitted formal change request documentation for client approval and monitored post-implementation queues for alert reduction.

Technical Analysis & Telemetry Insights

In high-volume multi-tenant SOC operations, false positive alert floods degrade analyst alertness and jeopardize Service Level Agreements (SLAs). However, improper or overly broad rule suppression introduces severe blind spots that attackers can exploit. Tuning detection logic requires an audit methodology grounded in verifiable entity baselines:

1. Repetition Clustering: Grouping recurring alerts over a 14-day or 30-day baseline reveals noisy rule patterns, frequently generated by scheduled vulnerability scanners, automated backup scripts, health monitors, or endpoint inventory tools. 2. Verification of Legitimate Business Need: Before any exclusion is drafted, the analyst must verify asset ownership, confirmed maintenance windows, and authorized administrative scope directly with client IT stakeholders. 3. Scoped Multi-Field Exclusions: Broad exclusions (such as whitelisting an entire IP subnet or disabling a rule outright) are strictly prohibited. A defensible detection rule exclusion must be scoped to the intersection of multiple immutable attributes: cryptographic file hash (SHA-256) of the authorized utility, verified parent process path, specific source IP, and target destination port. 4. Detection Rule As Code & Versioning: Tuning changes should be modeled in Sigma or SIEM query repositories with clear comments, peer-reviewed by senior detection engineers, and monitored in staging for 72 hours before production commit.

Diagnostic Query / Logic Sample

title: Scoped Authorized Scanner Exclusion status: experimental detection: selection: src_ip: ["10.14.2.50"] user_agent|contains: "AuthorizedScanner"

Competencies & Value Demonstrated

  • Systematic false-positive reduction in multi-tenant MSSP detection environments
  • Preservation of detection integrity through strict multi-attribute scoping
  • Collaboration with client stakeholders to validate authorized IT administrative behavior
  • Backtesting detection rule modifications against historical SIEM datasets
  • Significant reduction in queue noise and SLA response time improvement

Incident Outcome & Verification Status

Verified Disposition

Successfully tuned 4 high-frequency detection rules with zero degradation to coverage. Shift queue false positive volume dropped by 38% across affected client tenants.
